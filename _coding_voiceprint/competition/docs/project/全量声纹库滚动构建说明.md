# 全量声纹库滚动构建说明

> 本文用于新会话接续实施“分批下载录音、角色识别、客户侧embedding、落库校验、删除原始录音”的全量声纹库构建任务。文中“已实现”表示当前代码和产物已经核验，“待实现”表示新会话必须完成后才能启动全量任务。

## 一、建设目标

在本地磁盘空间有限的条件下，按固定批次滚动处理录音：

```text
数据库游标取数
→ 下载本批录音
→ 实际音频质量校验
→ 双声道ASR与客服/客户角色识别
→ 仅客户侧CAM++ embedding
→ 批次向量与元数据原子落盘
→ 完整性校验
→ 删除本批原始录音和临时WAV
→ 推进游标并处理下一批
```

最终长期保留以下内容：

- 去标识化录音清单和处理状态。
- 客服/客户角色识别JSON。
- 客户侧192维embedding。
- 正式客户侧向量索引。
- 待复核样本及失败清单。
- 模型版本、阈值、批次游标、校验和及审计日志。

原始MP3和拆分WAV只作为批次临时文件，在通过删除门槛后自动清理。

冻结代理测试集578通，可判定542通，可判定准确率100%，覆盖率93.77%。该指标使用方向规则代理标签，不是人工逐通金标准确率。生产验收仍需至少200通分层人工双盲金标。

## 三、为什么只保留客户侧向量

滚动构建时应优先只保存当前判定的客户侧embedding，不再额外保留客服侧embedding。

原因如下：

- 人工复核改判客服/客户角色时，如需客服侧向量需要重新读取音频补算。
- 话术角色模型升级时，只需重新计算角色，不必重新运行客户侧CAM++。
- 低置信样本仅保留角色结果和必要追溯信息，不再额外保存客服侧embedding。
- 192维`float32`单向量约768字节，客户侧单向量已足够支撑当前正式索引。

双侧向量不能解决embedding模型本身升级的问题。CAM++版本变化后仍需重新读取音频，因此必须保留可追溯信息或确认上游录音长期可重新获取。

以下为待实现的版本化目录建议，必须放在现有`声纹对比/`模块内：

```text
声纹对比/

│       ├── library_manifest.json
│       ├── batch_index.jsonl
│       ├── role_results/
│       ├── embedding_batches/

│       ├── failure_queue.jsonl

```

不得直接覆盖现有`recent_voiceprints_10k_20260819/`或旧向量库。新库通过验收后再进行版本切换。

### 4.1 单条角色结果

正式角色JSON至少保存：

| 字段 | 说明 |
|------|------|
| `recording_id` | 由URL哈希生成的去标识录音ID |
| `source_id_sha256` | 源记录ID的SHA-256 |
| `url_sha256` | 原始URL的SHA-256 |
| `identity_sha256` | 客户号SHA-256；缺失时不得进入正式客户库 |
| `begin_time` | 录音时间，用于批次追溯 |
| `audio_sha256` | 已下载音频内容校验和 |
| `quality_status` | `valid_dialogue`、`one_sided`或`no_effective_dialogue` |
| `agent_ch` | `L`、`R`或空 |
| `customer_ch` | `L`、`R`或空 |
| `left_agent_probability` | L侧客服概率 |
| `right_agent_probability` | R侧客服概率 |
| `margin` | 两侧客服概率差 |
| `threshold` | 本次使用的冻结阈值 |
| `needs_review` | 是否进入人工复核 |
| `role_model_version` | 角色模型版本 |
| `asr_model_version` | ASR模型版本或模型路径版本标识 |
| `processed_at` | 处理完成时间 |

所有样本保留字符数、有效语音时长等数值摘要。完整ASR正文默认不进入正式角色JSON。

### 4.2 ASR正文保留策略

- 高置信有效样本：只保留数值摘要、概率和角色结果，不长期保存完整转录。
- 低置信样本：完整L/R转录可临时保存在受控`_temp/`目录，供人工复核。
- 空录音和单边录音：保留质量状态，不保存无意义正文。
- 转录可能包含手机号、姓名和业务内容，禁止写入模型卡、公开报告或普通索引文件。

### 4.3 embedding批次

每个embedding记录至少包含：

- `recording_id`
- `identity_sha256`
- `channel`，取客户声道的`L`或`R`
- `embedding`
- `dimension=192`
- `embedding_model=CAM++`
- `embedding_model_version`
- `role_model_version`
- `audio_sha256`
- `batch_id`
- `created_at`

缓存键必须包含`recording_id + customer_ch + embedding_model_version`。禁止继续仅用`recording_id.npy`判断缓存命中，否则角色变化后可能错误复用旧向量。

全量库不应生成完整N×N矩阵。N条录音的矩阵空间和计算量为`O(N²)`，只适合抽样评估。全量1:N查询应构建独立检索索引，具体采用FAISS、HNSW或现有检索实现需在新会话检查本地依赖后确定，并记录最终方案。

## 五、滚动批次流程

### 5.1 批次规模

建议初始批次为1,000通。现有数据平均每1,000通原始MP3约306 MiB，但运行时还会产生拆分WAV和检查点，必须保持至少10至15 GiB磁盘余量。

批次规模必须可配置，连续两个批次稳定后再评估是否扩大。不得以牺牲磁盘安全余量换取吞吐。

下载阶段可以通过`--download-workers`提高并发，当前默认值为8；ASR、角色判断和embedding仍保持串行处理，避免把模型推理并发引入不稳定因素。

如果需要暂停下载、只继续当前临时批次的角色识别与后续提交，可以使用`--resume-last-temp-batch`直接恢复最近的`_temp/full_voiceprint_build/batch_*`目录，不再重新拉新候选。

### 5.2 数据分页

当前下载脚本只对最新候选执行固定`LIMIT`，不能覆盖全量数据。启动全量任务前必须实现：

1. 冻结本次构建的时间上界和时间下界。
2. 使用`begin_time + id`稳定游标做键集分页，不使用不稳定的大OFFSET分页。
3. 每批完成并清理后才推进游标。
4. 使用全局`url_sha256`去重，避免跨批次重复下载。
5. 游标、批次边界、候选数、成功数、拒绝数和失败数原子写入`batch_index.jsonl`。
6. 任务恢复时从最后一个已提交批次继续，不重新处理已提交批次。

当前候选排序已经验证为`begin_time DESC, id DESC`。分页SQL必须沿用同一稳定排序，具体SQL需在实现后补单元测试并执行只读验证。

### 5.3 单批处理步骤

1. 创建唯一`batch_id`和临时批次目录。
2. 只读查询下一页候选，不将原始URL、客户号写入持久化普通日志。
3. 下载MP3并校验文件SHA-256、实际时长、采样率和声道数。
4. 对L/R分别执行ASR，生成临时文本和数值摘要。
5. 使用`role-text-v1-20260820`判断角色和质量状态。
6. 仅对识别出的客户声道提取CAM++ embedding。
7. 对客户侧向量执行维度、有限值和归一化校验。
8. 原子写入本批角色JSON、embedding批次和状态清单。
9. 执行批次验收；只有全部通过后才提交批次游标。
10. 根据删除门槛自动删除本批MP3、临时WAV和无须保留的完整转录。
11. 记录释放空间、正式入库数、待复核数、剔除数和失败数。

### 5.4 正式入库规则

样本必须同时满足以下条件才能进入正式客户向量索引：

- `identity_sha256`非空。
- L/R均满足20字符和5秒有效语音门槛。
- 角色结果为`identified`。
- `margin >= 0.817575`。
- 客户声道对应embedding存在。
- embedding维度为192。
- embedding全部为有限数值。
- embedding模型与正式库版本一致。
- 元数据和向量校验和匹配。

以下样本不得进入正式客户索引：

- 空录音或双方均无有效对话。
- 单边有效语音。
- 低置信角色结果。
- 客户身份哈希缺失。
- ASR、角色判断或embedding失败。
- 模型版本或向量维度不一致。

待复核样本只保留角色结果、必要追溯信息和受控ASR摘要，不生成客服侧或候选客户侧embedding，必须与正式索引隔离。

## 六、原始录音删除门槛

删除必须由流水线执行，不得在处理未完成时手工批量删除。每个文件只有同时满足以下条件才能删除：

1. 下载清单存在且`audio_sha256`校验通过。
2. 角色质量状态已经落盘。
3. 所有需要保留的客户侧向量已经写入不可变批次文件。
4. embedding维度、有限值和模型版本校验通过。
5. 本批元数据数量与向量数量核对通过。
6. 批次文件已经完成原子重命名，不存在`.tmp`文件。
7. 批次摘要已写入且可重新读取。
8. 全局去重索引和批次游标已提交。
9. 删除目标解析后的绝对路径位于当前批次临时目录内。
10. 删除后重新统计磁盘空间并记录清理结果。

失败样本和待复核样本的删除策略标记为`[待确认]`。如果仍需人工听音，不得删除原始录音；如果只允许查看ASR并且上游录音可重新获取，可以在保存角色结果和可追溯信息后删除。

## 七、可追溯与重新处理

当前清单不保存原始URL、客户号或源记录ID，只保存对应SHA-256、`begin_time`和文件哈希。该设计减少敏感信息落盘，但无法通过清单直接重新下载单条录音。

删除原音前必须确认以下恢复方案之一：

- 上游表长期保留录音记录和URL，可按批次时间范围重新查询，并在内存中计算`source_id_sha256`或`url_sha256`完成匹配。
- 保存受控加密的源定位信息，密钥和访问方式需另行审批并记录。

上游表及URL的保留周期目前为`[待确认]`。在该问题确认前，应明确接受“embedding模型升级时可能无法重提历史音频”的风险，不能在文档中假设上游永久可用。

## 八、必须先完成的代码改造

新会话启动全量任务前，至少完成以下事项：

| 优先级 | 改造项 | 当前问题 | 验收条件 |
|------|------|------|------|
| P0 | 键集分页和批次游标 | 当前下载器只取固定最新候选 | 连续分页无重复、无漏页，支持断点恢复 |
| P0 | 客户侧embedding | 只需搭建客户声纹库，不保留客服侧向量 | 角色识别后仅对`customer_ch`提取并保存一个CAM++向量 |
| P0 | 缓存键版本化 | 当前分片只按录音ID命名 | 缓存键包含声道和模型版本 |
| P0 | 删除门槛 | 当前无完整提交后清理流程 | 失败注入时不误删，成功批次自动释放原音 |
| P0 | 正式库与待复核隔离 | 旧批次曾为全部成功判角样本提向量 | 低置信和无效样本不进入正式索引 |
| P1 | 批次向量格式 | 单一NPZ反复重写不适合持续扩展 | 不可变批次文件加全局索引，可独立校验 |
| P1 | 可追溯恢复 | 哈希清单不能直接下载单条录音 | 明确并测试一种受控恢复路径 |
| P1 | 检索索引 | 全量N×N不可扩展 | 构建1:N索引并保留抽样评估能力 |
| P1 | 监控与统计 | 当前摘要为单批口径 | 输出累计、批次、质量、拒识、失败和空间统计 |

建议新增编排脚本`pipelines/build_full_voiceprint_library.py`，测试统一放入`tests/unit/`和`tests/integration/`。不得在项目根目录创建新的业务目录。

## 九、测试要求

### 9.1 单元测试

- 游标分页边界，同一时间多条ID的稳定顺序。
- URL跨批次去重。
- 下载中断和处理进程中断后的恢复。
- 空录音、单边录音、低置信录音的隔离。
- 仅客户侧向量保存，未识别客户声道时不生成embedding。
- 缓存键包含声道和模型版本。
- embedding维度、非有限值和归一化异常拒绝。
- 原子写入失败时不推进游标、不删除原音。
- 删除目标越界时强制拒绝。
- 已提交批次重复执行时保持幂等。

### 9.2 小批集成测试

先用20至50通执行完整闭环：

1. 下载。
2. ASR和角色判断。
3. 客户侧embedding。
4. 正式与待复核分流。
5. 原子提交。
6. 删除原音。
7. 重启后验证不会重复处理。
8. 随机抽样核对角色JSON、向量和源哈希关联。

小批闭环通过后再运行1,000通，连续两个1,000通批次无错误后才能继续维持1,000通节奏。

### 9.3 全量验收指标

每批和累计报告至少包含：

- 候选数、下载成功数、实际音频拒绝数和网络失败数。
- 有效双边、单边、无有效对话数量。
- 角色可判定数、待复核数、覆盖率和概率差分布。
- 客户侧embedding成功数、失败数和模型版本。
- 正式入库录音数、正式身份数、每身份模板数分布。
- 重复URL数、重复录音内容哈希数。
- 删除录音数、释放空间和剩余空间。
- 批次耗时及ASR、embedding分阶段耗时。

人工准确率必须单独使用金标集报告，不得用呼叫方向代理一致率替代。

## 十、运行安全约束

- 数据库只允许执行只读`SELECT`，每次SQL执行按项目规范追加到`WORKLOG.md`。
- 不执行建表、插入、删除或修改生产数据库。
- 原始URL、客户号、手机号和姓名不得写入普通日志、报告或正式模型产物。
- embedding属于敏感生物特征数据，正式目录应限制访问，并保留版本、审计和校验信息。
- 完整ASR正文属于敏感内容，只允许在受控临时目录中按需保存。
- 任何递归删除前必须校验绝对路径位于当前批次临时目录。
- 旧库在新库验收前保持只读，不覆盖、不删除。
- 不允许边观察冻结测试结果边调参；角色模型调整只能使用训练集和验证集。

## 十一、新会话执行顺序

新会话应按以下顺序推进，不要直接启动大批下载：

1. 阅读本文件、`声纹对比/README.md`和项目根目录`AGENTS.md`。
2. 检查现有下载、角色判断和embedding脚本，确认新话术模型入口。
3. 建立实施计划，并先完成第八章所有P0改造。
4. 新增单元测试并运行`声纹对比/tests/unit/`全部测试。
5. 用20至50通执行删除前后的闭环集成测试。
6. 核对正式库、待复核区、失败区和游标恢复。
7. 执行两个1,000通试运行批次。
8. 汇报空间、耗时、覆盖率、失败率和正式入库率。
9. 经确认后扩展到1,000通滚动批次并持续构建。
10. 每次阶段完成后更新`WORKLOG.md`，只记录真实执行结果。

## 十二、新会话启动提示

可在新会话中直接提出：

```text
请阅读 声纹对比/docs/全量声纹库滚动构建说明.md、声纹对比/README.md 和 AGENTS.md，按说明先完成全量声纹库滚动构建的P0代码改造与测试。不要直接开始大批下载；先完成键集分页、客户侧embedding、版本化缓存、正式/待复核隔离和安全删除门槛，再用20至50通做闭环验证。所有数据库操作只允许SELECT，执行后更新WORKLOG.md。
```
